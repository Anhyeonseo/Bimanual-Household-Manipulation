# 수건 접기 인식 계획 — 흐트러진 상태 전제

## 1. 과제 정의

수건 **한 장**을 접는다. 단, **넓게 잘 펴진 상태에서 시작하지 않는다.**
흐트러진 상태에서 시작해 **펴기와 접기를 번갈아 반복**한다. 한 번에 접히지
않으며 매 단계마다 상태가 바뀌므로 재인식이 전제다.

- 테이블 위에서 접는다. 공중에서 양팔로 드는 것이 아니다
  (`RL_INTEGRATION_REQUIREMENTS.md:198`). 적재 하중은 작지만 **뻗은 낮은
  자세가 상시 조건**이고 그 영역이 처짐이 가장 심하다
- 양팔이 동시에 서로 다른 지점을 다룬다
- 과제 허용치는 펜보다 **훨씬 헐겁다**. 제약은 정밀도가 아니라 **안전 게이트**
  가 된다 (`RL_INTEGRATION_REQUIREMENTS.md:202`)

## 2. 흐트러진 상태가 왜 다른 문제인가

펜 pick-and-place 와 같은 도구로 풀리지 않는 이유가 셋이고, 이것이 이 계획의
구조를 결정한다.

1. **상태를 압축할 수 없다.** 펼쳐진 수건은 모서리 4개로 기술되지만 흐트러진
   수건은 압축 표현이 없다. 겹치고 자기 자신을 가리며 아래 층은 관측 불가다.
2. **역모델이 없다.** "X 에 놓고 싶다 → 여기 잡고 저기로" 가 펜에서는
   계산되지만, "펴고 싶다" 에는 **어디를 잡고 어느 방향으로 당길지 닫힌 해가
   없다.** 접촉이 지배하고 차원이 높다.
3. **목표가 좌표가 아니다.** "평평함" 은 좌표로 쓸 수 없는 성질이다.
   `RL_INTEGRATION_REQUIREMENTS.md:197` 이 이미 지적했다 — "펜은
   `lift_height + hold_time + distance` 로 되지만 접힘은 그렇게 안 된다".

## 3. 카메라 분업 원칙

**손목 카메라는 세계 어디로 갈지 결정하지 않는다. "내 손끝 상태가 지금
어떤가" 만 답한다.**

| | 담당 | 근거 |
|---|---|---|
| **Top-view** | 전역 상태, 어디를 잡을지 | 어디를 잡을지 고르려면 전체를 봐야 한다. 실측상 좌표 정확도는 이미 충분하다 |
| **Wrist** | 손끝 국소 상태 (검증 + 국소 기하) | Top 이 원리적으로 못 보는 것만 담당 |

### 왜 손목이 절대 좌표를 정하지 않는가 — 2026-08-09 실측

W3 eye-in-hand 보정 후 축별 오차:

| 축 | std | max\|dev\| |
|---|---|---|
| X | 3.06 mm | 6.41 mm |
| Y | 2.35 mm | 5.95 mm |
| **Z** | **5.65 mm** | **9.13 mm** |

- 전체 잔차 `6.81 mm` 의 대부분이 Z 다. 평면 표적 단안 깊이 관측성이 약하다
- 이 오차에는 카메라 보정 오차만이 아니라 **팔 자신의 FK 오차(처짐)가 섞여
  있다.** C2 는 SHOULDER 처짐만 `7.42 mm` 로 실측했고 같은 크기다
- **처짐은 base 절대좌표로 올렸다 내리는 과정에서만 섞인다.** 카메라가
  그리퍼에 강체로 붙어 있으므로 **그리퍼 기준 상대 측정은 처짐과 무관하게
  정확하다.** 이것이 아래 모든 역할을 그리퍼 좌표계로만 정의하는 이유다

### 흐트러진 상태에서는 손목 가치가 **올라간다**

펼쳐진 상태에서는 top-view 만으로 충분하다. 그런데 흐트러지면 정반대가 된다:

- 평평할 때는 위에서 봐도 한 겹인 것이 자명하다
- **뭉쳐 있으면 위에서 한 겹인지 세 겹인지 구분이 거의 불가능하다** — 2D
  실루엣이 같다
- 잘못 집을 확률이 오르고, 그것을 잡아낼 수 있는 것은 손끝 카메라뿐이다

즉 **손목 카메라의 검증 가치는 천이 지저분할수록 커진다.**

### wrist_roll 30° 제한 — 미검증 소프트웨어 상속값 (2026-08-09)

R2(edge 각도 → `wrist_roll` 보정)의 실효성을 "허용치 ±15°" 로 낮게 잡았던
전제를 재검토한다. **그 값은 기계적 한계가 아니라 한 번도 제대로 측정하지
않은 값이었다.**

- URDF 실제 한계(`so101_arm_macro.xacro:393`)는 `-4.3146..+1.2704 rad`
  ≈ **320°**. `config/single_arm_calibration.json` 이 쓰는 raw
  `1874..2219`(≈30°)는 URDF 허용치의 9% 뿐이다
- 근거로 인용됐던 `2026-07-30-physical-range-revalidation.md` 재측정
  세션에서 SHOULDER/ELBOW는 실제로 끝까지 돌려보고 범위를 넓혔지만,
  WRIST_ROLL은 **그 세션 안에서 7 raw(0.6°)밖에 안 움직여보고** "기존
  유지"로 넘어갔다. 즉 소프트웨어 관례가 검증 없이 상속된 값이다
- BASE도 같은 세션에서 `2164..2315`(151 raw)만 관측하고 범위를
  확정했다. URDF는 `±1.91986 rad`(220°)를 허용하는데 현재 운용은 54.7°
  뿐이다 — 같은 상속 패턴일 가능성이 높다
- 진짜 제한 후보는 **손목 카메라 USB 케이블**이다. 마운트 부모 링크가
  `gripper_link`(`so101_arm_macro.xacro:327`)라 카메라가 `wrist_roll`과
  같이 돈다. 이 케이블을 단 뒤로는 재측정한 적이 없다

**이것이 풀리면 두 가지가 동시에 해소된다**: (a) 조 yaw 자유도가 30°에서
최대 320°까지 늘어나 5절 R2의 실효성이 바뀌고, (b) BASE 범위가 넓어지면
아래 "문제 A"(저높이 도달영역이 수건보다 작음) 자체가 완화되거나 사라질
수 있다. 재측정 절차는 폭이 아니라 안전 순서다: 토크 DISABLE 전 팔을
반드시 사람이 받친 상태에서, wrist_roll과 BASE를 양방향 끝까지 천천히
돌려 케이블 간섭·기계적 스톱을 관찰하고 관측 끝값에 64 raw 여유를 두고
적용한다(SHOULDER/ELBOW 때와 같은 규칙). 8절 우선순위 1번.

## 4. 손목 카메라 역할 — 검출만 하고 대응이 없으면 만들지 않는다

"조용한 반복도 조용한 포기도 없다" (`PLAN_CONVERGENCE_AND_BIMANUAL.md` 7절).
각 역할에 대응을 함께 정의한다.

| | 성격 | 잡는 실패 | 대응 |
|---|---|---|---|
| **R1 겹 수 판정** | 범주 | 한 겹 잡아야 하는데 두 겹 집음 / 허공 | 놓고 살짝 옆에서 재파지 |
| **R2 edge 각도** | 연속값 | 모서리가 조와 비스듬히 물려 fold 선이 삐뚤어짐 | `wrist_roll` 조정 후 fold |
| **R3 장력·주름** | 연속값 | 늘어진 채 접혀 fold 가 뭉개짐 | 양팔 간격 조정 |
| **R4 이상 감지** | 이진 | top-view 가 말한 위치와 실제가 크게 다름 | 정지·보고 (재계획) |

- **R1 이 이 과제의 핵심**이다. 흐트러진 상태의 지배적 실패 유형이고 top 이
  원리적으로 못 본다
- **R2 는 손목 카메라가 유일하게 동작을 개선하는 자리**다. 나머지는 실패를
  감지할 뿐이다
- **R3 는 투기적이다.** 아래 6절 위험 참고
- **R4 는 이미 만들어져 있다** — `tools/wrist_visual_correction.py`

## 5. 기술 선택

### 5.1 R1 — 검출 문제를 분류 문제로 바꾼다

**카메라가 그리퍼에 강체로 고정이므로 손가락 사이 영역은 항상 이미지의 같은
픽셀에 있다.** 천을 "찾을" 필요가 없다.

- 입력: **고정 ROI** crop, `64×64`~`96×96`
- 출력: `empty` / `one_layer` / `multi_layer` 3-class
- 모델: tiny CNN. 상단이 `320×320` YOLO11n-OBB 를 Pi 에서 4Hz 로 돌리고 있으니
  이보다 훨씬 작은 분류기는 예산에 거의 안 잡힌다
- 배포: 상단과 같은 경로 — ONNX + `cv2.dnn.readNetFromONNX`, `DNN_TARGET_CPU`.
  검증된 런타임이라 새 의존성이 없다

### 5.2 R2 — 각도는 위치보다 관측하기 쉽다

**그리퍼 조 방향이 이미지에서 고정 방향**이다. 따라서

    조에 대한 모서리 기울기 = 이미지에서 모서리 각도 − 상수

캘리브레이션 정확도가 개입할 여지가 거의 없다. 그리고 대응 DOF 가 정확히
하나 있고(`wrist_roll`), **그것을 푸는 함수가 이미 리포에 있는데 프로덕션
호출자가 없다** (`tools/grasp_yaw_kinematics.py:212 solve_wrist_roll()`).
가동범위가 재측정으로 넓어지면(위 "wrist_roll 30° 제한" 참고)
`within_limits`가 대부분 참이 되어 이 절이 본래 의도대로 동작한다. 재측정
전까지는 좁은 범위를 그대로 가정하고 개발하되, top-view 후보 필터에서
±15°를 벗어나는 모서리 방향은 우선순위를 낮추는 정도로만 반영한다(강한
배제는 하지 않는다 — 재측정 결과로 곧 바뀔 값이다).

리포 관례를 따라 두 백엔드로 만든다 — 상단이 `detector_backend` 파라미터로
classical 윤곽 baseline 과 YOLO OBB 를 갈아끼우는 것과 같은 구조:

1. **classical 먼저**: gradient orientation / 선 검출 → PCA 주방향. 학습
   데이터 없이 즉시 시작하고 baseline 수치를 남긴다
2. **learned 나중**: 얇은 edge segmentation → 선 적합. classical 이 부족한
   것이 수치로 증명된 뒤에만

### 5.3 예산과 phase

`config/camera_schedule.json` / `cameras.yaml` 에 총 추론 `12 Hz` 캡과 phase
별 게이팅이 이미 구현돼 있다. 캡처(V4L2 MJPEG)는 3대 다 켜도 싸고 비싼 것은
추론뿐이다.

- **R1/R2 는 파지 순간 전후 1~2초만 필요하다.** 상시 추론이 아니라 이벤트성
  이라 예산 부담이 실질적으로 매우 작다
- 접근·전역 인식 구간은 top 만, 파지 직전은 해당 팔 wrist 만, fold 실행은
  양쪽 wrist

**실제 갭**: 기존 phase 이름
(`APPROACH_RIGHT` / `VISUAL_ALIGN_RIGHT` / `VERIFY_RIGHT`)이 **한 팔씩 순차
처리** 모양이다. 수건은 양팔 동시라 phase 어휘를 다시 설계해야 한다
(`DUAL_PRIVATE` 가 양쪽 `5 Hz` 로 유일하게 이 모양이다).

## 6. RL 의 자리

### 무엇을 배우게 하는가

**"어디를 잡고 어느 방향으로 얼마나 당길지" 를 정하는 것.** 2절의 이유로
계산으로 유도할 수 없고, 한 번에 끝나지 않는 순차 결정이다.

RL 이 **하지 않는** 것도 분명하다 — trajectory 생성은 여전히 MoveIt2 몫이고
RL 은 목표 선택만 한다.

### 관절 제어를 배우게 하지 않는다

흐트러진 천을 펴는 정책을 raw 관절 제어로 처음부터 학습하는 것은 연구
프로젝트 규모다. 훨씬 작은 문제로 줄인다:

- **스크립트된 smoothing primitive** 를 손으로 만든다 — "보이는 모서리 하나
  잡고 바깥으로 당기기", "양팔로 마주 잡고 펴기" 등. 각 primitive 실행은 기존
  MoveIt2 + buffered trajectory 파이프라인이 그대로 한다
- **학습은 "지금 상태에서 어느 primitive 를 어디에 적용할지" 선택만** 한다.
  연속 제어가 아니라 이산 선택이라 학습 규모가 몇 자리 줄어든다
- 이 방향이 이미 계약에 있다 — `policy_deployment_contract.json` 의
  `action.allowed_representations` 에 **`arm_selection`** 이 들어 있다

### 손목 카메라는 raw 픽셀이 아니라 파생 특징으로 들어간다

- `policy_deployment_contract.json` 은 `rgb_tensor` / `hybrid` 를 허용하고
  `allowed_camera_order: [top, wrist_a, wrist_b]` 를 이미 선언했다
- 그런데 `config/camera_schedule.json` 의 `policy_runtime.raw_image_input`
  이 **`false`** 이고, 이것은 설정값이 아니라 **검증기와 시험으로 강제**된다
  (`tools/validate_camera_schedule.py:56`, `tests/test_validate_camera_schedule.py:34`)
- 예산도 안 맞는다: `intra_op_threads: 1`, `default_rate_hz: 10`,
  `maximum_inference_p95_ms: 80`, `onnxruntime_cpu`. 이 안에서 카메라 3대 raw
  이미지를 vision backbone 으로 통과시키는 것은 현실적이지 않다

따라서 **R1/R2 출력을 저차원 특징으로 넣는다** (`hybrid`):
`layer_class` 3-class, `edge_angle_rad` 스칼라, `grasp_present` bool.

이렇게 하면 넷이 동시에 해결된다 — 예산에 부담 없음, **sim2real 갭이 작음**
(raw 픽셀이면 사실적 천 렌더링 + 이 카메라 왜곡 `k1=-0.456` + 그리퍼 가림까지
재현해야 한다), 샘플 효율, 그리고 검증된 계약을 흔들지 않음.

**R1/R2 는 이중 역할을 한다** — 지금은 명시적 판정 계층, 나중에 그대로 policy
관측 특징. RL 을 나중에 하기로 해도 지금 만드는 것이 낭비가 아니다.

### 선행 블로커 (카메라와 무관)

- `RL_INTEGRATION_REQUIREMENTS.md:195-196` — **변형체 시뮬레이션이 없다.**
  현재 env 는 강체 상자다. 수건을 학습시킬 환경 자체가 없다
- `:163-165` — 현재 env 는 `privileged_state` 로 물체의 참 위치를 본다.
  카메라가 루프에 없다
- **오늘 풀린 것**: `:166` 의 "손목 카메라를 관측에 넣으려면 C3 완료가 선행"
  조건은 W3 완료로 해제됐다

## 7. 단계

각 단계가 그 자체로 가치를 남기고 다음 단계의 전제가 된다.

### T0 — R1 실현 가능성 실험 (반나절, **갈림길**)

- [ ] 수건 `한 겹` / `두 겹` / `없음` 상태로 손목 카메라 이미지 각 30~50장
- [ ] 고정 ROI crop 을 떠서 **눈으로 먼저** 구분되는지 확인
- [ ] 구분되면 간단 분류기로 수치 확인

**이것을 제일 먼저 하는 이유**: R1 은 본질적으로 깊이 문제인데 이 리그에는
깊이 센서가 없다. 겹 경계의 그림자·edge 단서에 의존하므로 **RGB 로 될지
장담할 수 없다.** 여기서 신호가 없으면 R1 을 depth 센서 문제로 넘기고 손목
카메라를 R2+R4 로 축소한다. 전체 계획의 갈림길이라 가장 싸게 먼저 확인한다.

### T1 — R2 classical baseline + `solve_wrist_roll` 배선

- [ ] 학습 없이 edge 각도 추출 (classical)
- [ ] `solve_wrist_roll()` 을 실제 호출 경로에 연결 — 리포에서 유일하게
      "계산은 되는데 안 쓰이는" 코드를 살린다
- [ ] 경계와 fail-closed 는 `wrist_visual_correction.py` 정책 형태를 따른다

### T2 — R4 배선

## 8. 지금 진행 상황에서의 접점

손목 카메라 트랙은 `docs/checklists/WRIST_CAMERA_EYE_IN_HAND.md` 기준으로
W0(optical frame) ~ W3(eye-in-hand solve) 완료, W4 판정 계층 완료 상태다.

### 실측이 다시 정리한 세 문제

이 계획 전체가 놓인 제약을 세 개로 좁힌다. 셋 다 인식 알고리즘이 아니라
하드웨어·데이터 문제라 순서가 인식 작업보다 앞선다.

- **문제 A — 저높이 도달영역이 수건보다 작다.** BASE 스윕 54.7° ×
  반경 0.30 m ≈ 호 방향 290 mm, 반경 방향 180 mm. 일반 핸드타월은 한
  팔로 못 덮는다. → 수건 규격을 250~300mm 정사각으로 과제 규격으로
  고정하거나(단기), BASE 재측정으로 220°까지 회복되는지 확인한다(3절
  "wrist_roll 30° 제한" 참고, 근본 해법)
- **문제 B — 그리퍼 인코더로 천 파지 여부를 확인할 수 없다.**
  `tools/execute_gripper_command_once.py:71` 실측: 빈 close 잔여
  `5 raw`, 펜(25mm) close 잔여 `23 raw`. 천 한 겹(1~2mm, 압축됨)의
  잔여 차이는 빈 close 노이즈 바닥 아래로 들어간다. **R1(손목 카메라
  겹 수 판정)은 "있으면 좋은 검증"이 아니라 파지 확인의 유일한 수단이다**
  — 4절의 "R1 이 핵심" 근거를 이걸로 대체한다
- **문제 C — 평평한 부분보다 뭉친 부분을 노려야 한다.** 자세별 처짐이
  최대 20mm(SHOULDER 32raw)인데 목표 두께가 펼쳐진 천 2mm면 처짐
  오차 안에 묻힌다. 뭉친 부분(높이 있는 곳)을 잡으면 목표 두께가
  20~30mm로 올라가 처짐 오차와 같은 규모가 된다. top-view mask의
  거리변환만으로 후보를 뽑을 수 있다(4절 T4)

### 우선순위

1. **wrist_roll + BASE 물리 가동범위 재측정** (3절) — 반나절, 성공하면
   문제 A와 R2 유효 범위가 동시에 풀린다. 투자 대비 회수가 가장 크다
2. **grasp offset 재스윕** (카메라 단 상태, 물리) — 펜 파지가 "항상 덜
   내려감"으로 실패하는데 방향이 일관되므로 시각 문제가 아니라 offset
   문제다. 유력 원인은 카메라 질량으로 처짐 프로파일이 바뀐 것(W0
   불일치 5번). A4/A5 때 `PICK_GRASP_OFFSET_M 0.017→0.011`과 같은 절차
3. 수건 규격 확정 (1번 결과 반영)
4. **T0** R1 실현 가능성 (갈림길)
5. **T1** R2 + `solve_wrist_roll` 배선
6. T2 → T3 → T4 → T5

## 9. 이 계획이 지키는 규율

`PLAN_CONVERGENCE_AND_BIMANUAL.md` 7절을 그대로 이어받는다.

- **상수를 늘리지 않는다.** 실패할 때마다 값을 키우는 대신 왜 틀렸는지 측정
  한다. W4 의 `8 mm` 하한이 그렇게 나왔다 (평균으로 잡았다가 오탐 4/10 을
  실측하고 최악값으로 다시 잡았다)
- **검출만 하고 대응이 없는 기능은 만들지 않는다.**
- **층을 섞지 않는다.** top 은 어디로 갈지, 손목은 손끝 상태, 수렴 루프는
  도달 여부를 각각 답한다
- **못 하는 것을 못 한다고 적는다.** R1 의 RGB 실현 가능성과 R3 는 지금
  불확실하며 그렇게 표시해 둔다
