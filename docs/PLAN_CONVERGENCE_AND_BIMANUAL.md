# 도달 수렴 계층 — 한 팔 최종안이자 양팔의 토대

2026-08-06 A4.5 가 인식 좌표로 하강했으나 물체를 집지 못했다. 원인은 인식도
yaw 도 아니었다. 손가락은 펜을 `10.7도` 오차로 가로질렀고 검출 흔들림은
`0.77 mm` 였다. **팔이 명령받은 자세에 `1.68도` 못 미쳤고, 반경 `0.40 m` 에서
그것은 `11.7 mm` 였다.**

이 문서는 그 문제를 임시로 덮지 않고 최종 구조로 푸는 방법을 정한다.

## 1. 무엇이 진짜 문제인가

시스템이 자세를 명령하고 **도달했다고 가정**한다. post-settle 이 오차를 재긴
하는데 보고만 하고 아무것도 하지 않는다. 수락 기준 `30 raw` 는 반경 `0.4 m`
에서 `19 mm` 로, 펜 파지가 요구하는 정밀도보다 한참 헐겁다.

A4 에서 `PICK_GRASP_OFFSET_M = 0.017` 이 맞았던 것은 그 회차의 처짐이 작았기
때문이다(post-settle `14 raw`). A4.5 는 `19 raw` 였다. **offset 은 상수가
아니며, 다시 재도 다음 위치에서 또 틀린다.**

### 원인이 하나가 아니었다 (2026-08-06 추가 측정)

C1 을 시작하며 FK 를 붙여 검증하다가 **세 번째 오차원**을 찾았다. 위 서술은
처짐만 원인으로 보고 있었는데 그것으로는 부족했다.

`ros_moveit_plan_grasp.py` 는 목표를 점이 아니라 **상자**로 준다.

```python
region.dimensions = [2.0 * position_tolerance_m] * 3   # 기본값 0.006
```

MoveIt 은 그 상자 안 아무 데나 들어가면 `success` 를 돌려준다. 즉 축당
`6 mm`, 모서리로는 `10.4 mm` 를 **계획 시점에 이미 허용하고 있었다.** 그리고
그 값은 계획 artifact 에 기록조차 되지 않아, 증거 파일만 봐서는 그 계획이
`6 mm` 틀려도 되는 계획이었다는 것을 알 수 없었다.

실제로 재보니 2026-07-30 계획의 IK 해는 요청 좌표에서 `6.3` / `8.0 mm`
떨어져 있었다. **A4 파지 창 전체가 `8 mm` 였는데 같은 크기다.**

조이면 IK 가 실패할 것이라는 우려는 측정으로 기각됐다. 작업영역 5개 좌표 ×
허용치 7단계(`0.006`..`0.0002`) × 3회 = **105회 계획 요청이 전부 성공**했고
잔차는 허용치를 그대로 따라갔다.

| 허용치 mm | 성공 | 축 최대 잔차 mm |
|---|---|---|
| 6.00 | 15/15 | 5.67 |
| 4.00 | 15/15 | 3.71 |
| 2.00 | 15/15 | 1.92 |
| 1.00 | 15/15 | 0.98 |
| 0.20 | 15/15 | 0.19 |

기본값을 `0.001` 로 조인 뒤 실측 grasp 잔차는 `4.599 mm` → `0.982 mm` 다.
**아무 대가 없이 파지 예산에서 3.6 mm 가 빠졌다.**

따라서 오차원은 셋이고 층이 다르다.

| 오차원 | 크기 | 어디서 생기나 | 누가 닫나 |
|---|---|---|---|
| 계획 잔차 | 종전 ≤6 mm/축 → 현재 ≤1 mm/축 | 계획 시점 허용 상자 | 허용치를 조이고 잔차를 게이트 |
| 추종 오차(처짐) | A4.5 실측 11.7 mm | 실행 시점 중력 하 정상상태 | **이 문서의 수렴 계층** |
| 인식 오차 | 표본 흔들림 0.77 mm | 검출 | W3/W4 (C3) |

**`PICK_GRASP_OFFSET_M` 이 상수가 아니었던 이유가 이것으로 더 정확해진다.**
그 값은 처짐만이 아니라 **계획 잔차와 처짐의 합**을 그 회차에서 흡수하고
있었고, 둘 다 자세마다 달라진다.

아래 2절의 "8 mm 창 → ±4 mm → 6 raw" 유도는 **명령 공간**에서 잰 것이라
이 두 오차가 섞여 있다. 과제 허용치 `4 mm` 자체는 유지하되, 이제는 raw 로
환산하지 않고 **FK 로 구한 TCP 변위를 직접 미터로** 판정한다. 관절 오차를
`raw × 반경` 으로 환산하면 어느 관절이 틀렸는지에 따라 답이 달라지기
때문이다.

### 두 층이 섞여 있다

| 층 | 답해야 할 질문 | 현재 |
|---|---|---|
| **자기수용** | 팔이 명령받은 자세에 실제로 가는가 | 하지 않음. 30 raw 허용하고 보고만 |
| **외부수용** | 그 자세가 올바른 자세인가 | 손목 카메라 미적용 (W3/W4) |

지금은 offset 하나로 둘 다 때우려 하고 있다. **아래층을 고치지 않으면 위층의
일이 정의되지 않는다** — 손목 카메라가 목표를 아무리 잘 고쳐도 팔이 그 목표에
`12 mm` 못 미치면 보정이 무의미하다.

## 2. 허용치는 둘이어야 한다

하나의 숫자가 두 가지 다른 질문에 답하고 있다. 갈라야 한다.

| 허용치 | 뜻 | 소유자 | 값 |
|---|---|---|---|
| **안전 허용치** | 동작이 잘못되지 않았다 | buffered Action | `30 raw` (현행 유지) |
| **과제 허용치** | 이 파지는 성공할 것이다 | 과제 계층 | 파지별로 유도 |

Action 이 안전하지만 정밀하지 않은 동작을 실패로 만들면 안 된다. 충분히
정밀한지는 **과제가 판단한다.** 지금은 `POST_SETTLE_TOLERANCE_RAW = 30` 이
`buffered_action_execution.py` 의 모듈 상수라 이 구분이 불가능하다.

펜 파지의 과제 허용치는 A4 스윕에서 유도한다. `0.025`(TCP z `0.0313`)에서
놓치고 `0.017`(`0.0233`)에서 잡혔으므로 창은 `8 mm` 안이다. 절반을 여유로
잡으면 `±4 mm`, 반경 `0.4 m` 에서 **약 `6 raw`** 다.

## 3. 수렴은 어디에 사는가

세 후보를 놓고 보면 답이 하나로 좁혀진다.

- **runbook(셸)** — 지금 당장은 빠르지만 확장되지 않는다. 양팔이 되면 복사본이
  둘이 되고 갈라진다.
- **bridge 의 Action 안** — 매력적이지만 **bridge 는 계획하지 않는다.** 보정은
  현재 anchor 에서 같은 목표로 **새 궤적을 만드는 일**이고 그것은 계획이다.
  게다가 Action 이 궤적 종료 후에 팔을 더 움직이면 그 계약이 예측 불가능해지고,
  물리 검증을 마친 계층을 흔들게 된다.
- **host 측 라이브러리** ← **채택.** 계획이 필요하고, 재시도 횟수와 넘겨명령
  크기는 정책 결정이며, 정책은 과제 계층의 것이다.

Action 은 "이 궤적을 그대로 실행하고 어디서 끝났는지 정직하게 보고한다" 를
유지한다. 그 정직함이 수렴의 입력이다.

## 4. 수렴 알고리즘

```
1. 계획된 자세로 하강                     (기존 segment leg 파이프라인)
2. post-settle 관절 오차 측정             (Action 이 이미 보고함)
3. 과제 허용치보다 크면
     같은 목표로 경계된 짧은 보정 leg 1회, 최대 N회
4. 오차가 더 줄지 않고 **정체**하면
     남은 잔차만큼 넘어서 명령한다
         target' = target + (target - measured)
     경계된 1회. 상한을 넘으면 실행하지 않는다
5. 그래도 부족하면 fail-closed 로 멈추고 잔차를 보고한다
```

**4 번이 최종안의 핵심이다.** 중력 하 정상상태 오차는 계통적이므로 실측한
잔차만큼 넘겨 명령하면 상쇄된다. 적분 동작을 모델이 아니라 **그 회차의
실측값으로, 경계된 1회**만 수행한다.

짧은 보정 leg 가 잘 동작한다는 것은 이미 관측됐다 — A4 의 `4 s / 201 sample`
leg 는 모델 peak 오차 `0.000`, post-settle `14 raw` 였다.

### 왜 이것이 최종안인가

- **모델이 없다.** 자세·부하·온도가 달라도 매 회 실측으로 맞춘다
- **기존 파이프라인을 그대로 쓴다.** `plan_buffered_segment_leg.py` 가 짧은
  보정 이동에 그대로 맞는다
- **수렴하지 못하면 그렇게 말한다.** 정체를 감지해 잔차와 함께 멈춘다.
  조용히 반복하지 않는다
- **층이 겹치지 않는다.** 나중에 W4 가 *목표* 를 고치고 이 루프가 *도달* 을
  보장한다. 실패했을 때 어느 쪽 문제인지 갈린다

### 버린 대안

| 안 | 버린 이유 |
|---|---|
| offset 을 더 크게 | 자세마다 다르다. 2026-08-06 에 겪은 것이 정확히 이것 |
| 관절 한계 여유 게이트 | A4 **성공** 자세도 `WRIST_FLEX` 가 하한에서 `7 raw` 였다. 성공 회차를 거부했을 것 |
| P-gain 상향 | Shoulder P32 / Elbow P28 로 이미 조정했다. 진동 대비 여유가 작다 |
| 처짐 모델 학습 | 보정 데이터가 많이 필요하고 부하·온도로 흘러간다. 실측 1회가 더 정확하다 |
| pregrasp 경유로 짧게만 이동 | 변경은 작지만 원인을 고치지 않는다. 긴 이동이 필요한 순간에 재발한다 |

## 5. 지금 양팔 모양으로 만들어야 하는 것

싸게 지금 하거나, 비싸게 나중에 되돌리거나다.

### 프로토콜은 이미 준비돼 있다

`ACTUATOR_BUFFERED_COMMAND_UNSUPPORTED_RIGHT_SLOT` 와 arm mask 검사가 이미
있다. 와이어 형식이 오른팔 슬롯을 예약하고 명시적으로 거부한다. 양팔은 MCU
수준에서 예견돼 있다.

### host 는 준비돼 있지 않다

| 항목 | 현재 | 되어야 할 것 |
|---|---|---|
| `POST_SETTLE_TOLERANCE_RAW = 30` | 모듈 상수 | 목표별 인자, 팔별 계약값 |
| `left_arm_controller` 등 | 하드코딩 | 팔 이름으로 매개변수화 |
| 처짐 보정값 | 없음 | **팔별**로 유지. 두 팔의 처짐은 다르다 |
| 수렴 실행 | 없음 | **동시 실행 가능**해야 한다 |

마지막 항목이 중요하다. 팔 A 를 수렴시키고 팔 B 를 수렴시키면 주기가 두 배가
된다. 라이브러리 API 를 **보내기와 판정하기로 분리**해 두 팔을 겹쳐 돌릴 수
있게 만든다. 나중에 합치려면 구조를 다시 짜야 한다.

### 조율된 중단

팔 A 가 수렴에 실패했는데 팔 B 가 물체를 들고 있으면 둘 다 멈춰야 한다.
`docs/CURRENT_STATE_AND_NEXT_ROADMAP.md` D절의 "한 팔 fault 시 양팔 coordinated
stop" 이 그것이며, 수렴 실패도 그 fault 목록에 들어간다.

### 비동기 host 송신이 더 급해진다

`0x00022900` 이 남긴 여유는 `0.312 ms`, 전선 기준 4바이트 미만이다. 양팔이면
acknowledgement 트래픽이 두 배가 되어 그 여유가 사라진다. 수렴 루프는 짧은
leg 를 더하므로 Action 수도 늘어난다. **양팔 진입 전 필수** 로 이미 기록돼
있으나, 이 계획이 그 시급성을 높인다.

### C2 — 한 팔 실기 검증 — **완료 2026-08-06**
- [x] 고정 위치에서 수렴 동작 확인 — pregrasp/grasp 두 자세에서 재현.
      ELBOW 오차 18/16 raw → **0**. 잔차 15.74→10.00, 11.04→5.98 mm
- [x] 처짐 실측을 자세별로 기록 — 두 자세 모두 **SHOULDER** 가 지배
      (7.42 / 3.61 mm). 넘겨명령으로도 이 관절만 개선되지 않는다
- [x] **파지 성공** — 잔여 간격 `22 raw`. 다만 offset 을 다시 재야 했다:
      `0.017` 은 처짐을 흡수하던 값이라 수렴 후에는 헛닫혔고, 3 mm 스윕으로
      `0.011` 을 얻었다
- [x] **A4.5 재시도 통과** — 인식 → 수렴 → 파지 전 구간. 인식 15표본
      흔들림 `1.65 mm`, 수렴 `11.19 → 7.75 mm`, 파지 잔여 간격 `21 raw`.
      손가락 교차각 `86.28도`(이상 90도)라 손목 보정 없이 성립했다

**허용치에 대한 판단이 바뀌었다.** 파지는 잔차 `10.17 mm` 에서 성립했다.
과제 허용치 `4 mm` 는 파지 성공의 필요조건이 아니다. 수렴의 값은 잔차를
`0` 으로 만드는 데 있지 않고 **작게 만들고 측정 가능하게** 만드는 데 있으며,
남은 잔차는 offset 이 흡수한다. 그것이 성립하려면 잔차가 **회차 간 재현**
되어야 하고, A4 가 실패한 이유도 잔차가 컸기 때문이 아니라 회차마다 달랐기
때문이다. 다음 질문은 "4 mm 안에 넣을 수 있는가" 가 아니라 **"얼마나
재현되는가"** 이며 그것은 A5 pilot 의 몫이다.

기록: `docs/test-results/2026-08-06-c2-convergence-physical.md`

### C3 — 손목 카메라 (외부수용 층)

### C4 — 한 팔 최종 산출물

- A5 10회 pilot. 회차별 증거와 잔차 기록
- **여기까지가 독립적으로 가치 있는 결과다.** 양팔 없이도 "정해진 물체를
  반복해서 집어 옮긴다" 를 증거와 함께 주장할 수 있다

### C5 — 양팔 진입 전 필수 (별도 트랙, 병행 가능)
- 비동기 host 송신 (여유 `0.312 ms` 제거)
- 비동기 servo I/O + 타이머 ISR executor
- 오른팔 슬롯 활성화
- 조율된 중단

## 7. 이 계획이 지키는 규율

- **상수를 늘리지 않는다.** 실패할 때마다 값을 키우는 대신 왜 틀렸는지
  측정한다
- **허용치의 소유자를 나눈다.** 안전은 Action 이, 정밀도는 과제가 판단한다
- **수렴하지 못하면 말한다.** 조용한 반복도, 조용한 포기도 없다
- **양팔 모양을 지금 만든다.** 팔별 상태와 동시 실행은 나중에 끼워 넣기 어렵다
- **층을 섞지 않는다.** 도달과 목표는 다른 문제이고, 섞으면 실패 원인을 가른
  수 없다
