# C1 — 도달 수렴 계층 (하드웨어 없음)

2026-08-06 · 데스크탑 전용 · 물리 실행 없음 · `motion_authorized: false` 유지

전체 회귀 **841 통과** (세션 시작 756).

## 왜 했나

A4.5 가 인식 좌표로 하강했으나 펜을 집지 못했다. 인식은 정확했고(표본 흔들림
`0.77 mm`) 손가락도 펜을 가로질렀다(`10.7도` 오차). **팔이 명령받은 자세에
`1.68도` 못 미쳤고 반경 `0.40 m` 에서 그것은 `11.7 mm` 였다.**

시스템이 자세를 명령하고 도달했다고 가정하는 것이 문제였다. post-settle 이
오차를 재긴 하지만 보고만 하고 아무것도 하지 않는다.

## 하려던 것과 실제로 나온 것

계획은 "처짐을 수렴으로 닫는다" 였다. FK 를 붙여 검증하는 과정에서 **원인이
하나가 아니었음**이 드러났다.

### 1. FK 검증 — 어긋난 쪽은 IK 였다

`grasp_yaw_kinematics.py` 에 TCP 위치 FK 를 넣고 2026-07-30 계획 artifact 의
IK 해를 넣어보니 요청 좌표와 `6.3` / `8.0 mm` 어긋났다. FK 버그를 의심해
MoveIt 자신의 `/compute_fk` 에 같은 관절값을 물었더니 **소수점까지 동일한
값**이 나왔다(`-3.4061, +3.0090, +4.3159` mm).

FK 는 맞았다. 어긋난 것은 계획이었다.

### 2. 원인 — 목표가 점이 아니라 상자였다

```python
# tools/ros_moveit_plan_grasp.py
region.dimensions = [2.0 * position_tolerance_m] * 3   # 기본값 0.006
```

MoveIt 은 그 상자 안 아무 데나 들어가면 `success` 를 돌려준다. 축당 `6 mm`,
모서리로는 `10.4 mm` 가 **계획 시점에 이미 허용되고 있었다.** 그리고 그 값은
계획 artifact 에 기록조차 되지 않아, 증거 파일만 봐서는 그 계획이 `6 mm`
틀려도 되는 계획이었다는 것을 알 수 없었다.

**A4 파지 창 전체가 `8 mm` 였는데 같은 크기다.**

### 3. 조이면 IK 가 실패하는가 — 측정으로 기각

작업영역 5개 좌표 × 허용치 7단계 × 3회 = **105회 계획 요청, 105회 전부 성공.**

| 허용치 mm | 성공 | 축 최대 잔차 mm |
|---|---|---|
| 6.00 | 15/15 | 5.67 |
| 4.00 | 15/15 | 3.71 |
| 3.00 | 15/15 | 2.96 |
| 2.00 | 15/15 | 1.92 |
| 1.00 | 15/15 | 0.98 |
| 0.50 | 15/15 | 0.50 |
| 0.20 | 15/15 | 0.19 |

증거: `docs/test-results/evidence/2026-08-06-plan-position-tolerance-sweep.json`

기본값을 `0.001` 로 조인 뒤 같은 펜 좌표로 재계획한 실측:

| | 종전 0.006 | 현재 0.001 |
|---|---|---|
| pregrasp 잔차 | 6.532 mm | 1.419 mm |
| grasp 잔차 | 4.599 mm | 0.982 mm |

**아무 대가 없이 파지 예산에서 3.6 mm 가 빠졌다.**

## 오차원은 셋이고 층이 다르다

| 오차원 | 크기 | 누가 닫나 | 상태 |
|---|---|---|---|
| 계획 잔차 | ≤6 mm/축 → ≤1 mm/축 | 허용치 조이기 + 잔차 게이트 | **닫힘** |
| 추종 오차(처짐) | A4.5 실측 11.7 mm | 수렴 계층 | 구조 완성, C2 실기 대기 |
| 인식 오차 | 표본 흔들림 0.77 mm | W3/W4 | C3 |

`PICK_GRASP_OFFSET_M` 이 상수가 아니었던 이유가 이것으로 더 정확해진다. 그
값은 처짐만이 아니라 **계획 잔차와 처짐의 합**을 그 회차에서 흡수하고 있었다.

## 만든 것

### 계획 잔차 게이트 — `tools/ros_moveit_plan_grasp.py`

- `--position-tolerance` 기본값 `0.006` → `0.001`
- 계획 후 `/compute_fk` 로 해의 실제 TCP 를 재서 `achieved_tcp_m`,
  `plan_residual_m`, `plan_residual_norm_m`, `plan_residual_axis_maximum_m`
  를 artifact 에 기록
- `plan_residual_bound_m` 을 **허용치에서 유도**한다
  (`tolerance × √3 × 1.16`). 손으로 정한 두 번째 허용치가 아니라 상자 기하가
  허용하는 최악값이며, 넘으면 solver 가 제약을 지키지 않았거나 FK 모델이
  계획 모델과 다른 것이다. 둘 다 조용히 넘어가면 안 되는 사건이므로
  `success = false` 로 거부한다

### 관절별 실측 보존 — `buffered_action_execution.py`

`_verify_post_settle` 는 목표·실측·관절별 오차를 전부 계산해두고 `max()` 하나만
남기고 버렸다. **그래서 A4 성공 회차와 A4.5 실패 회차의 도달 자세를 지금
되살릴 수 없다.**

`PostSettleMeasurement` 를 추가해 종단 문자열에 실어 보낸다.

```
post_settle_target_raw=... post_settle_measured_raw=... post_settle_error_raw=...
```

- `post_settle_max_error_raw` 는 종전과 **정확히 같은 수**이고 Action 의 판정
  논리는 바뀌지 않았다. 덧붙이기만 했다
- sender 가 파싱해 `TerminalEvidence` 에 담고, `|실측 − 목표| ≠ 오차` 이면
  거부한다
- 벡터 최대는 보고된 최대값을 **넘을 수 없다** (같을 필요는 없다 — 보고값은
  position-only 스냅샷과 최종 full diagnostics 중 큰 쪽이다)
- 옛 형식으로 기록된 증거도 계속 읽힌다

`tests/test_buffered_terminal_format_contract.py` 가 형식 드리프트를 잡도록
설계돼 있었고, 실제로 이 변경에서 **가장 먼저 깨졌다.**

### 수렴 라이브러리 — `tools/grasp_convergence.py`

순수 판정 함수다. 계획하지 않고 움직이지도 않는다.

```
1. 과제 허용치 안이면        -> accept
2. 보정 한계를 넘으면         -> fail  (처짐이 아니라 실행 오류다)
3. 오차가 커지면              -> fail  (발산)
4. 반복 예산 소진             -> fail
5. 아직 줄고 있으면           -> correct   (같은 목표를 짧은 leg 로 다시)
6. 정체했으면                 -> overshoot (target' = target + (target-measured), 1회)
7. 넘겨명령 뒤에도 정체하면    -> fail
```

**보정과 넘겨명령이 다른 이유.** 보정은 명령을 바꾸지 않고 **출발 위치만**
바꾼다 — 훨씬 가까운 곳에서 출발하므로 동적 오차가 작아진다(A4 의 `4 s /
201 sample` 짧은 leg 가 model peak 오차 `0.000`, post-settle `14 raw`). 그것이
통하지 않게 되면 남은 것은 중력 하 정상상태 오차이고 계통적이므로, 모델을
세우지 않고 **그 회차의 실측 잔차만큼** 넘겨 보낸다.

**오차는 언제나 원래 목표에 대해 잰다.** 명령을 바꿔가며 그 명령에 대해
재면 팔은 언제나 "거의 도달" 로 보이면서 실제 목표에서는 멀어질 수 있다.

경계값과 근거:

| 값 | 크기 | 근거 |
|---|---|---|
| 과제 허용치 | 4 mm | A4 스윕: 위로 8 mm 는 확실한 실패, 0 mm 는 성공. 절반 |
| 최대 반복 | 3 | 조용히 반복하지 않는다 |
| 최대 보정 | 30 mm | A4.5 실측 11.7 mm 보다 크되, 그보다 훨씬 크면 처짐이 아니다 |
| 정체 기준 | 1 mm | 계획 잔차(~1 mm)보다 작은 개선은 잡음이다 |
| 넘겨명령 상한 | 15 mm | 관측된 최대 잔차 11.7 mm 를 덮되 크게 튀지 않는다 |

**예산이 닫힌다.** 계획 잔차 `0.982` + 과제 허용치 `4.000` = `4.982 mm`
< 확실한 실패점 `8 mm`. 계약 validator 가 이 산술을 강제한다.

### 두 허용치를 갈랐다

| 허용치 | 질문 | 소유자 | 값 |
|---|---|---|---|
| 안전 | 동작이 잘못되지 않았다 | buffered Action | `30 raw` (**변경 없음**) |
| 과제 | 이 파지는 성공할 것이다 | 과제 계층 | `0.004 m` |

`buffered_trajectory.py` 는 안전 허용치 값을 베껴 적지 않고
`buffered_action_execution` 에서 **정의 자체를 import** 한다.

### 양팔 모양

- `ConvergencePolicy` 는 팔 이름이 필수다. 빈 이름은 거부된다
- 정책이 팔별이다 — 두 팔의 처짐은 같지 않다
- `evaluate()` 는 아무것도 보내지 않는다. 두 팔의 결정을 각각 구한 뒤
  `arms_requiring_motion()` 이 돌려주는 팔들을 **동시에** 움직인다.
  순차로 수렴시키면 주기가 팔 수만큼 배가 된다
- `any_failed()` 가 조율된 중단의 입력이다
- `grasp_yaw_kinematics.py` 는 `prefix` 로 매개변수화됐다. 시험이 코드 본문에
  `left_` 가 남아 있지 않음을 강제한다

## 열린 것

- **과제 허용치 `4 mm` 는 아직 실기에서 확인되지 않았다.** 계약에
  `task_tolerance_confirmed_on_hardware: false` 로 적혀 있다. 수렴이 실제로
  그 안에 들어오는지는 C2 에서 잰다. 못 들어오면 값을 키우는 것이 아니라
  왜 못 들어오는지가 잔차로 보고된다
- A4 파지 창의 **경계**는 여전히 재지 않았다. `0.017` 성공, `0.025` 실패만
  알고 그 사이는 모른다. 물체 크기가 바뀌면 다시 재야 한다
- 수렴 실행기(`execute_*`)는 아직 없다. C2 에서 기존
  `plan_buffered_segment_leg.py` 파이프라인에 이 라이브러리를 붙인다
